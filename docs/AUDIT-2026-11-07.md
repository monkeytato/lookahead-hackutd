## Correctness bugs

**C1. Forecast includes the script's future (prophetic prediction).** Critical. VERIFIED.
- Evidence: `#/stage` at T+0 shows "Next loss: Level-2 chilled-water riser… in 4 min · 48 of 48 racks lost by T+60". The scenario's own step says the leak is "unobserved, no sensor on Level 2" (`src/domain/fixture.ts:287`).
- More evidence: `#/app/facility` and `#/present` show "IF NOTHING CHANGES first rack lost at 02:54 · 48 racks by 03:10" under the banner "All readings normal". `predictionSummary`/`simulateScenario` run every scheduled fault (`src/domain/engine/fixes.ts:180-199`). Only fix *options* are gated on observability (`fixes.ts:115`).
- Impact: the "prediction before the problem exists" is replayed foreknowledge.
- Direction: forecast only from faults observed or inferred by time t. Present scheduled faults as a "scenario script", never as a prediction.

**C2. The with/without comparison uses the wrong scenario and ignores evidence.** Critical. VERIFIED (UI and a script repro).
- Evidence: `server/workflowHub.ts:76-79` always uses `scn-chiller-trip` (CH-1 trips, and in the what-if CH-2 trips too at +12) for "Cooling failure", and `scn-riser-leak` for everything else.
- The UI showed "Restart CH-1 manually · Without response 48 racks at risk · With response 0" right after the portable scan said "Readings disagree".
- Rerunning `predictFix` on a CH-1-only copy of the scenario gives `racksWithout: 0, racksWith: 0`.
- Impact: the operator is told the whole hall (48/48 racks) is at risk because of an assumed second failure, for an alert the evidence disputes.
- Direction: build the counterfactual from the injected incident alone, conditioned on the evidence verdict. Show the what-if assumption explicitly.

**C3. The verdict ignores the installed reading and uses arbitrary thresholds.** High. VERIFIED.
- Evidence: `server/workflowHub.ts:56-60` gives `confirmed` if the portable mean is ≥ 28 °C (or > 0.5 wet or vibration fraction), and `disagrees` otherwise. The installed value (34.2 °C, 30.8 °C, …) is never compared.
- The engine's own `compareReadings` (material gap > 3 °C, `src/domain/engine/verification.ts`, documented in `docs/ENGINE_CONTRACT.md:21`) is unused.
- An air probe is used to "verify" a *chiller supply* temperature (CH-1).
- Impact: the central differentiator is a single threshold, inconsistent with the team's own contract.
- Direction: route verdicts through `compareReadings` with metric-appropriate points. Refuse incidents the probe cannot physically measure.

**C4. The simulated rig makes every demo warning "disagree".** High. VERIFIED.
- Evidence: inject Temperature alert, Cooling failure and Water leak, then "Take simulated sensor scan". All three return "Readings disagree": 22.5 °C, 22.4 °C, and a floor fraction of 0.
- The vibration scan button is disabled with no explanation (`MonitorWorkspace.tsx:119`, `frame.vibrating` is undefined on the sim).
- The `priority()` sort (`MonitorWorkspace.tsx:16`) then ranks "disagrees" *below* fan vibration, so a water leak drops to the bottom.
- Impact: the default demo tells judges the chiller failure and the leak are probably sensor faults.
- Direction: make the sim respond to the injected incident (or the scanned asset), or default the demo path to the labelled reference.

**C5. Actor attribution is fake or spoofable.** High. VERIFIED.
- Evidence: `src/state/workflow.ts:41` sends `actor: 'Priya Raman'` for every command. In History, the assignee Marcus's checklist ticks, the Nemotron analysis and the "demo alert" are all attributed to Priya Raman.
- The server trusts `body.actor` (`server/workflowHub.ts:24`). A probe with `actor: 'Spoofed Person'` was logged verbatim.
- The assignment event reads "assigned to emp-marcus" (raw id).
- Direction: take the actor from a session or a device identity picker. Log names, not ids.

**C6. The Nemotron question is truncated: log context never arrives.** High. VERIFIED.
- Evidence: the evaluate question built at `server/workflowHub.ts:74` was 955 characters in a repro (incident, fixture evidence, one operator note).
- `createSession` cuts `question` to 500 characters (`server/director/tools.ts:136`). "Recent recorded actions" started at character 596 and the operator note at character 914, so both were dropped.
- Direction: pass events as structured input (a tool or field), not as a prose suffix to a capped string.

**C7. Split state between tabs.** High. VERIFIED.
- Evidence: with CH-1, PIPE-L2 and CRAH-2 open in Operations:
  - Gauges shows "All readings normal", "hottest rack 23.1 °C Normal" and "CRAH fan vibration 1.4 mm/s Normal".
  - Sensor inventory shows "Hall A Normal · All sensors normal".
  - Phone `#/m` "Now" shows only the stage's A-11 issue, while its "Director" tab shows the workflow's CH-1 plan.
- Gauges, Facility, Inventory and Mobile read `OpsProvider`/stage. Operations reads `useWorkflow` (`src/state/workflow.ts`).
- Direction: make the injected workflow incidents drive the stage readings (or the reverse), or hide the stage tabs during the main demo.

**C8. CRAH units are displayed as racks.** High. VERIFIED.
- Evidence: `src/views/plain.ts:31-32` maps both `CRAH-n` and `A-n` to `Rack-n`.
- In the Operations map, the marker for the selected CRAH-2 reads "Rack-2", next to "Selected: CRAH-2".
- The lab equipment list has 24 entries but only 12 unique labels. Legacy tasks show "Vibration check on Rack-2 fan".
- Direction: drop the CRAH rule and keep the row letter for racks.

**C9. Phone-scanner scans are never attached.** Medium. VERIFIED (code).
- Evidence: `MonitorWorkspace.tsx:45-52` attaches only the `scanId` the laptop started. Scans from `#/scan` are broadcast but ignored by the workflow.
- `src/scan/ScanApp.tsx` asset list lacks CH-1, CH-2, P-1, P-2, GEN, ATS and UTIL, and offers no vibration point. That would fail `verify_scan`'s point regex (`server/workflowHub.ts:54`).
- Direction: let the scanner pick an open incident and attach through `verify_scan`.

**C10. Hard-coded rack total in the lab.** Medium. VERIFIED.
- Evidence: `src/views/Simulation.tsx:202` renders "`{n}` of 60 in total". The facility has 48 racks; it displayed "48 of 60".
- Direction: use the facility rack count.

**C11. Dead route in the More menu.** Medium. VERIFIED.
- Evidence: `src/app/TopBar.tsx:16` links to `#/app/team`. `AppShell` has no `team` section, so the page is blank. Any unknown `#/app/x` route is also blank, with no 404.
- `src/views/Team.tsx` exists but is unused.
- Direction: wire up Team or remove the link, and add a fallback route.

**C12. Fix-prediction cache is keyed only by scenario id.** Low. VERIFIED.
- Evidence: `src/domain/engine/fixes.ts:70`. A modified scenario object with the same id returned the original's results. This bit me while testing.
- Direction: include faults, leak and hazards in the key, or hash the scenario.

**C13. Unsigned "shift" invites inverted explanations.** Medium. VERIFIED.
- Evidence: `server/director/tools.ts:249-253` returns `Math.abs(x - y)`. Nemotron then wrote "abnormal reading confirms alarm as CORROBORATED, shifting first-rack loss 15.9 min later" (on the phone Director tab and in the analysis).
- It also stated "The rig is trustworthy" about the simulated rig.
- Direction: return signed deltas with direction words, and have the validator reject direction claims.

**C14. Workflow client ignores lower revisions.** Low. VERIFIED (code).
- Evidence: `src/state/workflow.ts:18` keeps local state if the server revision is lower. Suppose the bridge store is lost or corrupted (see D4) and restarts at revision 0. Open tabs then keep showing stale incidents and still say "Shared session connected" until a reload.
- Direction: include a session id and replace state when it changes.

**C15. Double-submit guard uses stale `busy`.** Low. SUSPECTED.
- Evidence: `command` checks `busy` from the render closure (`src/state/workflow.ts:32`). Two clicks in one frame both pass. The server rejects most duplicates, but checklist toggles would be logged twice.
- Direction: use a ref lock, as `evaluate` already does.

## Science / credibility of predictions

**S1. Intervals are overconfident even against the model's own perturbations.** Medium (#15). VERIFIED.
- Evidence: `reports/validation-2026-11-08-default.md`: p10–p90 coverage is 24% overall against an 80% target (chiller 4%, ATS 5%, `real-ovh-sbg2-2021` 0%).
- "First rack right" is 53%. The predicted fix benefit averages 32.1 racks saved against 23.6 realized.
- The harness (`scripts/validate/harness.ts:1-18`) compares the model with a *perturbed copy of itself*. It is a robustness check, not empirical validation.
- Direction: widen or calibrate the ranges, report coverage on screen, and stop calling the ranges "p10–p90" until coverage approaches the nominal value.

**S2. All-or-nothing outcomes.** Low. VERIFIED.
- Nearly every "without response" case loses 48/48 racks (UI and repro). Most validation fixes predict 48 saved.
- Losses are binary (lost at p50 or not), and on the shared chilled-water plant any sustained cooling loss takes the whole hall. That makes "racks at risk" a coarse, alarming number.
- Direction: show service and row granularity and time-to-impact, not just counts.

**S3. Edge delays and thermal constants are assumptions, and calibration is circular.** Low. VERIFIED.
- The fixture edge delays are labelled "assumption" (`src/domain/fixture.ts:146-150`).
- `src/domain/engine/thermal.ts:12-16` is "calibrated to agree with the cascade's thermal ride-through edges", which are themselves assumptions.
- `docs/ENGINE_CONTRACT.md:14` still documents the old formula (ΔTmax = 1.6·kW, τ = 4+60/kW).
- Direction: cite sources per constant, and update the contract.

**S4. Scenario mismatch.** VERIFIED (see C2).
- A-11 temperature and CRAH-2 vibration alerts are "evaluated" inside the riser-leak scenario at t=0, so Nemotron reasons about valves and UPS that have nothing to do with the alert. It said "no immediate valve/UPS action is warranted" for a rack inlet sensor.

**S5. "Real incident" framing.** Low. VERIFIED.
- The stage labels scenarios "REAL INCIDENT · ADAPTED & SIMULATED". The adaptations compress timelines, and fire and leak spread rates are assumptions. The labels are present, but a judge could read the "real" tag as validation.

## Security

**X1. No authentication; the LAN is exposed through the Vite proxy.** Medium (#13). VERIFIED.
- `server/index.ts:12` says it binds to 127.0.0.1. But `npm run dev:lan` runs `vite --host`, and `vite.config.ts:17` proxies all `/api` routes. Every route is therefore reachable from the LAN:
  - `/api/rig/command`: flap, valve and fan on real hardware (`server/index.ts:358-362`)
  - `/api/reset` and workflow `reset` (wipe the history)
  - `/api/actions/:id/approve` (executes agent-proposed rig commands or tickets; `by` is client-supplied)
  - `/api/director` (spends NVIDIA quota; 1 MB body; accepts client-supplied `scans`, contradicting the header's claim that "a client… never send[s] numbers")
- The README states "the bridge itself stays on 127.0.0.1", which is misleading.
- Direction: add a shared demo token, an Origin check and a LAN allowlist, and say so in the README.

**X2. CSRF.** Medium. VERIFIED.
- `readBody` parses JSON regardless of content type, and there is no Origin check. A `text/plain` POST (a CORS "simple request", so no preflight) to `/api/workflow` succeeded.
- Any web page open on the demo laptop could post to `localhost:5173` or `127.0.0.1:8787` to reset the session or command the rig.
- Direction: require `application/json` and verify `Origin`.

**X3. Input validation gaps.** Low. VERIFIED.
- `/api/scans/start` accepts unknown asset ids (`NOT-AN-ASSET` returned 200).
- `/api/frames?n=abc` returns the whole buffer.
- Director input errors return 500 instead of 400 (`server/index.ts:409-411`).
- `assign` was validated (good).

**X4. API key handling.** Low; no defect found. VERIFIED.
- `.env.local` is git-ignored (`.gitignore:27`), has never appeared in git history, and the key prefix appears in 0 files under `dist/`, `dist-artifact/`, `src/`, `server/`, `docs/` and `reports/`. `status()` exposes only the model and base URL.
- Minor: `server/env.ts:142-144` keeps inline `# comments` and trailing spaces in values, so a commented `.env.local` line would corrupt the key silently.
- Direction: strip comments and trim.

**X5. Prompt-injection surface.** Low. SUSPECTED.
- Operator notes and event summaries are interpolated into the Nemotron prompt (`server/workflowHub.ts:74`). The impact is limited because tools are whitelisted, actions need approval and numbers are validated.
- Direction: keep it as is, and mark user text as quoted data.

- `src/App.tsx:6` imports `AppShell` (and with it `Twin` and three.js) eagerly. `dist/assets/index-*.js` is 1.47 MB, possibly stale.
- Direction: lazy-load `AppShell`, as is already done for the other routes.

**P2. The 3D twin remounts per tab.** Low. VERIFIED.
- The map takes about 4–5 s to appear after switching between Operations and Facility. The heap was stable (70→63 MB over 6 switches) and there was a single canvas, so I saw no leak.

**P3. The engine is fine.** Low (informational). VERIFIED.
- `simulateScenario` runs in 45–84 ms per scenario in Node, and `visualAt` over 61 minutes in under 62 ms. The workflow polls every 1.8 s even though the bridge already broadcasts `workflow` revisions over SSE (`server/index.ts:270` vs `src/state/workflow.ts:28`).
